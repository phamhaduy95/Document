# Data Seeding in Entity Framework Core

Data seeding is the process of populating a database with an initial set of data. This is essential for providing lookup tables, default settings, or initial admin accounts required for the application to function.

---

## 1. Model Seed Data (Managed by Migrations)
This approach integrates seed data directly into the EF Core migrations. You define the data inside your `DbContext` using the **`HasData`** method.

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Role>().HasData(
        new Role { Id = 1, Name = "Admin" },
        new Role { Id = 2, Name = "User" }
    );
}
```

### Constraints of Model Seeding:
- **Manual Primary Keys**: You must explicitly provide values for primary keys, even if they are normally generated by the database.
- **Migration Bloat**: Seeded data is stored in the migration snapshots. Large amounts of data can lead to massive migration files and degraded performance.
- **Static Only**: This method cannot handle data that depends on database state or external services (like an API).

---

## 2. Custom Seeding Logic (Manual)
For complex scenarios—such as seeding initial users with hashed passwords or large datasets—it is better to use custom logic at application startup.

```csharp
public static async Task SeedDatabase(IServiceProvider serviceProvider)
{
    using var scope = serviceProvider.CreateScope();
    var context = scope.ServiceProvider.GetRequiredService<AppDbContext>();

    if (!context.Roles.Any())
    {
        context.Roles.Add(new Role { Name = "Standard" });
        await context.SaveChangesAsync();
    }
}
```

---

## 3. Choosing a Seeding Strategy

| Feature | Model Seeding (`HasData`) | Custom Seeding (Manual) |
| :--- | :--- | :--- |
| **Best Use Case** | Constants, lookup tables, configuration. | Test data, large datasets, dynamic content. |
| **Management** | Part of the migration file. | Part of the application code. |
| **Primary Keys** | Must specify manually. | Can be database-generated. |
| **Complexity** | Limited to static values. | Can use DI, hashing, and external calls. |

---

## 4. When to Avoid Model Seeding
It is recommended to use **Custom Seeding** if your data:
- Is temporary or only for testing purposes.
- Is very large (to avoid migration snapshot bloat).
- Requires password hashing (like ASP.NET Identity users).
- Requires the database to generate the identity keys.
